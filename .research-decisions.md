Net: Drizzle captures ~90% of Prisma's DX at a fraction of the setup and deploy risk, which is exactly the tradeoff this timebox rewards.

### Sharing / access-control model [sharing]
Recommendation: Ship a 3-table model — users, documents (with owner_id FK), document_shares (junction: document_id + shared_with_user_id + role enum) — and enforce EVERY read/write through a single server-only Data Access Layer (DAL) function requireDocAccess(documentId, session, minRole) that resolves the caller's effective permission (owner > editor > viewer) in ONE indexed SQL query and throws 403 before any data is returned or mutated. Use a role enum ('viewer','editor') from day one, not a boolean, because the incremental cost is ~15 minutes and it directly earns the 'access logic' and 'maturity' evaluation points that a boolean forfeits. Owner is implicit (documents.owner_id) — do NOT store an owner row in document_shares.
Rationale: The prompt rewards deliberate scope cuts AND explicitly evaluates 'access logic' and 'prioritization/tradeoffs.' A boolean (Option A) under-delivers on access logic; a generic ACL (Option C) over-delivers and eats the timebox. The role enum (Option B) is the maturity-per-minute sweet spot: it costs almost nothing over a boolean yet produces a demoable viewer-vs-editor distinction and a single symmetric permission check. Keeping owner implicit in documents.owner_id (not a share row) avoids a whole class of bugs — you never have to keep an 'owner share' in sync, an owner can never accidentally be un-shared, and self-shares are structurally impossible. The security core is NOT the schema — it's that every server entry point funnels through one DAL check. The 2026 Next.js guidance is unambiguous: middleware is not a security boundary (CVE-2025-29927 let attackers bypass it via an x-middleware-subrequest header), Server Actions and Route Handlers are directly POST-able public endpoints, so authorization MUST live in a server-only Data Access Layer that re-verifies the session and the specific object permission on every call. A page-level check alone is an IDOR waiting to happen. The exact pattern: requireDocAccess() calls verifySession() (server-only, React cache-memoized cookie/JWT check → throws 401 if no userId), then runs ONE query — SELECT d.*, CASE WHEN d.owner_id = $me THEN 'owner' ELSE s.role END AS effective_role FROM documents d LEFT JOIN document_shares s ON s.document_id = d.id AND s.shared_with_user_id = $me WHERE d.id = $docId — and if effective_role is null (no ownership, no share) it throws 403 (return a generic not-found to avoid leaking existence). Reads require minRole 'viewer'; writes/saves require 'editor' or 'owner'; rename/share/delete require 'owner'. Critically the WHERE always includes the current userId so the DB — not the app — filters foreign rows, closing the IDOR hole even if application logic slips. UI split is derived from the same source of truth, not a separate flag: 'My Documents' = WHERE owner_id = me; 'Shared with me' = documents JOIN document_shares WHERE shared_with_user_id = me. Never let the client send its own userId; always derive it from the verified session server-side.

Make three changes: (1) Promote the auth-identity substrate to a first-class, critical-path deliverable, not a risk footnote. Ship a signed, httpOnly cookie session (use iron-session or a signed JWT — do not hand-roll) seeded with 2-3 mock users, plus a visible user-switcher in the UI so a reviewer can toggle Alice<->Bob in one click and experience sharing from BOTH sides. verifySession() reads userId ONLY from this signed cookie; the client can never send its own userId. Jest's only real edge (maturity, larger plugin ecosystem) does not matter for a 4-6h build. Playwright is excellent but expensive here: browser install, a running dev server or a deployed URL, auth/session seeding, and flakiness against serverless cold starts. It does not add rubric points beyond the one meaningful test you already get from Vitest, so it is a poor use of the timebox unless the core is done early. The decisive design move is to keep authorization in a PURE function (e.g. `canView`/`canEdit`/`canRename(doc, sharesForDoc, userId)`) that takes plain data and returns a decision, with the route handler and DB query as thin adapters. That lets the meaningful test run as a fast unit test with zero DB/HTTP/mocking, while still asserting the exact logic that protects the API. One optional integration test can then exercise a route handler with a mocked/seeded data layer to prove the wiring, and one optional Playwright smoke can prove the deploy is alive.

### App architecture + deploy runbook [architecture-deploy]
Recommendation: Single Next.js 16 (App Router, TypeScript, Turbopack) app on Vercel + Neon serverless Postgres, using Drizzle ORM with the @neondatabase/serverless HTTP driver (neon-http). Layer the code as: thin Server Actions / route handlers -> service layer (business rules + authorization) -> repository layer (Drizzle queries) -> db client. Zod schemas live in a shared validation module and are enforced at the action/route boundary (never trust the client). Manage migrations with drizzle-kit generate (committed SQL) and a Node-runtime `db:migrate` script run manually (or as a Vercel build/predeploy step) rather than at request time. One Neon project with a dedicated preview branch for Vercel Preview and the primary branch for Production, wired via Vercel env vars per-environment.
Rationale: The prompt locks Next.js single-app + Neon + Vercel free tier and a 4-6h timebox, so the winning move is a structure that LOOKS like a real backend (clear action->service->repo->db seam, Zod at the edge, typed errors) without the cost of a separate service. Drizzle over Prisma: no separate engine binary, no `prisma generate` postinstall foot-gun on Vercel, faster cold starts on serverless, and drizzle-kit produces plain committed SQL migrations that are easy to reason about and review. The neon-http driver is the lowest-friction path on serverless (stateless HTTP, no connection-pool exhaustion, works in one round trip) which is exactly what a reviewer's ad-hoc testing hits. Server Actions are stable in Next 16 and let one developer ship CRUD + sharing mutations without hand-writing REST plumbing, while a couple of route handlers cover file upload and any fetch the client genuinely needs. The service layer is where owner/shared-access checks live so authorization is centralized and testable — which directly feeds the required automated test and the access-logic evaluation criterion. Keeping migrations out of the request path avoids the single most common first-deploy failure (neon-http can't run multi-statement migration files transactionally the way node-postgres can, and running migrate on cold start races concurrent lambdas).
