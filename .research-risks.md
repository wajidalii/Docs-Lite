### deployment
- (high/high) Missing or mis-scoped DATABASE_URL in Vercel: the build succeeds (no DB access at build time) but every request 500s at runtime, or the env var is set only for Production and Preview deploys are broken (or vice versa). This is the single most common first-deploy failure for Neon+Vercel. -> PREVENT: Add a fail-fast env guard in a single server-only db/env module that throws a clear, named error ('DATABASE_URL missing — set it in Vercel for Production and Preview') on import, so a missing var surfaces as an obvious message in logs instead of an opaque 500. Read DATABASE_URL only in this one place. Document the exact pooled connection string format in the README deploy section. | MITIGATE: Set DATABASE_URL (the pooled '-pooler' host, with ?sslmode=require) in Vercel for BOTH Production AND Preview environments. Verify with `vercel env pull` before pushing, and confirm the live app loads a document immediately after first deploy.
- (medium/high) Running DB migrations at build time or request/cold-start time. If migrate is wired into the Vercel Build Command or a request handler, concurrent lambdas race and neon-http cannot apply a multi-statement migration file transactionally the way node-postgres can, causing partial/failed migrations against the live Neon branch. -> PREVENT: Bake into the runbook: migrations are a manual, pre-deploy step (`npm run db:migrate` using drizzle-kit CLI, Node runtime, against the pooled URL). No migrate call anywhere in build config or request handlers. Commit generated SQL migration files so the reviewer's schema is reproducible. Document the 'run db:migrate once before first deploy' step explicitly in the README. | MITIGATE: Keep Build Command as plain `next build`. Apply schema exactly once, out-of-band: run `drizzle-kit generate` (commit the SQL), then `drizzle-kit migrate` locally against the Neon prod branch BEFORE deploy. Never migrate inside build or a request path.
- (medium/high) Edge runtime + Node driver mismatch. Importing the db client, iron-session, or isomorphic-dompurify (jsdom) into anything running on the Edge runtime — a route with `export const runtime='edge'`, or middleware — throws at deploy/runtime because these need Node APIs. -> PREVENT: Never add `export const runtime='edge'` to any file that touches db, iron-session, or dompurify. Do session/authz checks inside Server Actions and the DAL (Node runtime), NOT in middleware — this also aligns with the 'middleware is not a security boundary' (CVE-2025-29927) decision. Add `export const runtime='nodejs'` on the upload route from the start. | MITIGATE: Keep all db access, session handling, and HTML sanitization on the default Node.js runtime (Server Actions and route handlers are Node by default). For the upload/sanitize route handler, explicitly set `export const runtime = 'nodejs'`. Keep middleware db-free and session-free.
- (medium/high) TypeScript / @types version drift breaks the Vercel build. This sandbox reports bleeding-edge TS ('latest' 7.0.2) and @types/node 26, which produce type errors against the Next 16 toolchain (targets TS 5.x). The build passes with looser local settings but fails in Vercel CI where a clean install resolves the newest ranges. -> PREVENT: Commit an explicit package.json with the TS ^5.9 / @types/node ^24 guardrail and a committed lockfile, and gate the first push on a green local `next build`. Treat 'clean install + local build passes' as a hard precondition for deploy. | MITIGATE: Pin `typescript`:`^5.9` and `@types/node`:`^24` (caret, not the sandbox 'latest'). Run `npm install` + `next build` locally on a clean install BEFORE the first push so any type error surfaces locally, not in Vercel CI.
- (medium/medium) Neon SSL / wrong connection host. Using the non-pooled (direct) Neon URL, or omitting ?sslmode=require, yields connection errors or connection-exhaustion under a reviewer's concurrent clicking. -> PREVENT: Document the pooled-host requirement in the README, and in the env-guard module assert that the URL contains '-pooler' (warn if not) so a direct-host mistake is caught early. neon-http is stateless HTTP so pool exhaustion is largely structural-non-issue, but the correct host + sslmode still must be present. | MITIGATE: Copy the exact POOLED connection string from the Neon dashboard, including the '-pooler' host segment and ?sslmode=require, into DATABASE_URL for both environments.
- (medium/high) Missing SESSION_PASSWORD (iron-session secret) in Vercel env. Build succeeds, but iron-session crashes at runtime on the first login/session read because the encryption secret is unset or shorter than the required 32 characters. -> PREVENT: Read SESSION_PASSWORD in the same single env-guard module as DATABASE_URL, with a length check (>=32) and a clear error message. List both required env vars together in the README deploy checklist so neither is forgotten. Set cookie `secure:true` only in production so local http still works. | MITIGATE: Generate a >=32-char SESSION_PASSWORD and set it in Vercel for Production and Preview before first deploy. Add a startup guard that throws a clear named error if it is unset or too short.
- (low/medium) Preview vs Production configuration divergence. Vercel Preview deployments (from PRs/branches) may point at a different or unset Neon branch/env, so the reviewer testing a Preview URL sees failures the Production URL doesn't (or vice versa), and sharing/persistence appears broken. -> PREVENT: Give reviewers ONE canonical Production URL in the README. Use the Neon primary branch for Production; only wire a separate Neon preview branch if Preview deploys are actually used, and migrate it too. Keep the env-var set symmetric across environments so a Preview click never becomes the failing first impression. | MITIGATE: Decide up front which single URL reviewers test (Production). Ensure DATABASE_URL and SESSION_PASSWORD are set identically-in-shape for both environments, and run migrations against whichever Neon branch each environment points to.
- (low/high) Storing raw editor HTML leads to stored XSS and/or broken reopen after deploy — a correctness+security failure that only manifests on real shared content, not in a quick self-test. -> PREVENT: Lock persistence to JSON-only from the start and share one exported extensions array between the client editor and any server-side parse, so marks/nodes never silently drop. Point the required automated test at access-control (owner vs shared-viewer vs no-access) rather than styling, and keep the sanitize path Node-runtime if any HTML path is added later. | MITIGATE: Per the confirmed ui-ux decision, persist Tiptap JSON only and render read-only shared docs via a non-editable Tiptap (editable:false), eliminating the stored-HTML XSS path. If HTML is ever persisted, sanitize server-side with isomorphic-dompurify (resolved DOMPurify >=3.3.2, per CVE-2026-0540) on a Node-runtime handler.
- (low/medium) Server Action / upload body-size rejection on deploy. Vercel's 4.5MB request body cap and default Server Action body limit reject a larger .txt/.md (or a stretch .docx) with a 413, and the failure looks like a generic broken upload to a reviewer. -> PREVENT: Bake an explicit size/type guard (Zod) into the upload route with a friendly error message and a small cap well under 4.5MB, and surface the accepted types (.txt, .md) in the upload UI. Keep .docx flag-gated and cut first if the timebox tightens. | MITIGATE: Do uploads via a route handler that reads the file, decodes UTF-8, and validates size and type with Zod, returning a clear 4xx on violation. State supported types (.txt/.md) and an explicit small size cap in the UI and README.
- (low/low) Neon free-tier compute auto-suspends when idle; the first reviewer request after idle incurs a DB cold-start (a few hundred ms), which combined with a Vercel function cold-start can make the very first interaction feel slow or, in a worst case, brush a tight function timeout. -> PREVENT: Note the Neon idle-suspend cold-start in the README architecture note so reviewers read a slow first request as expected, not a bug. Keep queries single-round-trip (neon-http, no N+1) so total time stays well under the Hobby function limit; do not add long-running work to request handlers. | MITIGATE: Accept and document the cold-start as expected demo behavior. Because all queries are single-round-trip neon-http over text-sized data, they complete far inside the Hobby function timeout even with a Neon wake-up, so no timeout risk in practice.

### data-persistence
- (medium/high) Editor content does NOT round-trip losslessly on save/reopen — formatting (bold/italic/underline, headings, lists) is silently dropped because the server-side parse/render uses a different Tiptap extension set than the client editor, or because content is stored as HTML and re-parsed lossily. This directly violates the required 'formatting preserved' criterion. -> PREVENT: Bake JSON-only storage (content jsonb NOT NULL) + a single shared `extensions` module into the schema and TDD from line one. Add a Vitest test that takes a fixture doc with every required mark (bold/italic/underline, H1/H2/H3, bullet + numbered list), runs generateJSON->store->load, and asserts deep-equality of the JSON. | MITIGATE: Persist Tiptap ProseMirror JSON (not HTML) in a jsonb column and render read-only shared docs via Tiptap with editable:false from the SAME stored JSON. Export ONE shared extensions array (src/lib/editor/extensions.ts) imported by the client editor, the upload parser (generateJSON), and any server render, so round-trip is identity: getJSON() on save, content:json on load — no marks can be dropped.
- (medium/high) Debounced autosave race / lost update: rapid edits fire overlapping save requests over the stateless neon-http driver and an older in-flight write lands AFTER a newer one (out-of-order completion), silently overwriting the user's latest keystrokes. A save that fails mid-edit can also leave the user believing content persisted when it did not. -> PREVENT: In the TDD, make the autosave hook fire-once-at-a-time: hold a single in-flight promise, queue the latest content, flush on resolve. Add an updatedAt timestamptz column written on every save. Treat the save-status indicator as a first-class UI element, not polish. Explicitly cut real-time multi-user collaboration (documented scope cut) so last-write-wins is honest. | MITIGATE: Debounce saves (~800ms-1s); server does a single UPDATE keyed by doc id + verified editor/owner from the session (last-write-wins is fine for a single-user-at-a-time demo). Prevent OUT-OF-ORDER overwrites by serializing saves client-side (never issue save N+1 until N resolves; coalesce pending edits) or stamping each save with a monotonic updatedAt/sequence and rejecting stale writes server-side. Surface an explicit 'Saving… / Saved / Save failed — retry' status so a failed persist is never mistaken for success.
- (medium/high) Migration drift / schema-less production DB: `drizzle-kit migrate` is never run against the deployed Neon branch (or `drizzle-kit push` was used locally and diverged from committed SQL), so the live app queries tables/columns that don't exist and every read/write 500s on the first reviewer visit. Compounded because neon-http cannot apply a multi-statement migration transactionally, so a partial apply can half-build the schema. -> PREVENT: Bake `db:generate` / `db:migrate` npm scripts + committed drizzle/ SQL into the repo from the start, and make 'run db:migrate against the Neon prod branch' an explicit pre-deploy checklist item. Verify with a trivial SELECT against the deployed branch before announcing the live URL. | MITIGATE: Adopt generate+migrate (commit SQL from `drizzle-kit generate`) and apply it OUT-OF-BAND exactly once before deploy via `drizzle-kit migrate` against the Neon prod branch. Keep Vercel Build Command as plain `next build` — never migrate in build (avoids the concurrent-lambda race). Document the one-time migrate step in the README; never use `push` against prod.
- (medium/high) Neon connection / URL misconfiguration: DATABASE_URL is missing or mis-scoped in Vercel (set for Production but not Preview, or vice versa), the NON-pooled direct host is used, or `?sslmode=require` is dropped — build succeeds but runtime 500s, or connections exhaust under a reviewer's concurrent clicks. -> PREVENT: Add a Zod-validated env module imported by the db client so a missing/blank DATABASE_URL fails fast with a readable message at boot. Document the exact pooled + sslmode string shape in the README. Rely on neon-http's stateless-HTTP model (no pool lifecycle to leak) so this stays a config risk, not a concurrency risk. | MITIGATE: Use the Neon POOLED connection string (verify the '-pooler' host) with `?sslmode=require`; set DATABASE_URL in Vercel for BOTH Production and Preview; add a startup guard that throws a clear error if it is unset rather than failing deep inside a query. Keep all db access on the default Node.js runtime (never runtime='edge' on anything touching the db). Verify with `vercel env pull` before first push.
- (low/high) Data does not survive refresh because writes are optimistic-only on the client: the UI shows edits and share grants as applied, but the server action actually failed (validation, auth, or DB error) and the failure was swallowed. On refresh the edits/shares vanish — directly failing 'documents + sharing survive refresh'. -> PREVENT: Bake into the TDD that every mutation returns a discriminated success/error result and the client never assumes success. Add a manual (or optional Playwright) smoke step to the README: create a doc, edit + format, share with the second seeded user, hard-refresh, and confirm both content and share survive from the DB. | MITIGATE: Treat the server as source of truth: server actions/route handlers validate input with Zod at the boundary, return typed errors, and the client reflects success ONLY after the server confirms. On refresh, always re-fetch from the DB (no reliance on client/localStorage state). Surface a toast on any persist failure. For sharing, confirm the document_shares row is written and re-read the collaborator list from the DB after granting.

### editor-frontend
- (high/high) SSR hydration mismatch: Tiptap renders on the server during App Router SSR, producing markup that diverges from the client's post-hydration DOM. Surfaces as a React hydration error and, intermittently, a blank or duplicated editor. This is the single most common Tiptap + App-Router failure and it is dev-visible but easy to ship past if the guard is added late. -> PREVENT: Bake immediatelyRender:false + the null-guard into the editor component from the first commit, before any feature work. Write a first smoke test (RTL/jsdom) that mounts the editor component and asserts it renders without a hydration/act warning, so a regression that removes the flag fails CI. Treat this as a non-negotiable scaffold, not a fix-later item. | MITIGATE: In the 'use client' editor component set immediatelyRender:false in useEditor and guard with `if (!editor) return null` (confirmed as the official Tiptap SSR pattern in current v3 docs). Never render EditorContent before the editor instance exists. Keep the editor component a leaf client component, not imported into a server component's render path with server-only props.
- (high/high) Content round-trip fidelity loss via extension-set drift between the upload parser and the client editor. Upload parses .md/.docx -> HTML -> generateJSON on the server; if that server extension array differs from the client editor's extensions, unsupported marks/nodes (headings beyond H1-H3, lists, underline) are SILENTLY dropped from the stored JSON with no error. Same class of bug if two editor instances (edit vs read-only) configure extensions differently. -> PREVENT: Make the shared extensions module the FIRST editor artifact and forbid inline `extensions:[...]` anywhere else (grep-able rule). Write a test that round-trips a fixture doc containing every required mark/node (bold, italic, underline, H1/H2/H3, bullet + numbered list) through generateJSON -> stored JSON -> read-only render and asserts every node/mark type survives. This single test protects both upload fidelity and save/reopen fidelity. | MITIGATE: Export ONE shared extensions array (e.g. src/lib/editor/extensions.ts) and import it in every place a schema is constructed: the client edit editor, the read-only editor (editable:false), and the server-side generateJSON in the upload handler. Configure heading levels [1,2,3] once in that shared module. Persist JSON only (per the locked ui-ux decision) so there is no HTML<->JSON conversion on the normal save path.
- (medium/high) XSS via imported HTML on the upload/paste path. Even with JSON-only persistence eliminating stored-HTML XSS, the .md (and stretch .docx) import path produces HTML that is fed to generateJSON; markdown permits raw inline HTML and docx conversion emits HTML, so a malicious <script>/<img onerror>/javascript: URL can enter the schema if generateJSON is fed unsanitized HTML. Pasting rich HTML into the editor is the same surface. -> PREVENT: Put sanitize-then-parse in a single server-only import helper that is the ONLY way HTML becomes document JSON; no route may call generateJSON directly. Add a test feeding a hostile-HTML .md fixture and asserting the resulting JSON contains no script node and no javascript: href / on* attribute. Run `npm ls dompurify` + `npm audit` in the setup script so a downgraded transitive dompurify is caught. | MITIGATE: Sanitize HTML with isomorphic-dompurify (pinned >=3.19, resolved dompurify >=3.3.2 per CVE-2026-0540) on the Node runtime (export const runtime='nodejs') BEFORE generateJSON, and restrict the allowed schema to exactly the shared extension set so unknown/dangerous nodes cannot materialize. Because storage is JSON built only from the known schema, render read-only docs via Tiptap editable:false — never dangerouslySetInnerHTML.
- (medium/medium) Controlled-vs-uncontrolled state bug: re-passing changing `content` into useEditor (e.g. wiring the loaded doc as a reactive prop, or resetting content on every autosave/parent re-render) does not update Tiptap after mount and/or resets the cursor and clobbers in-flight edits. useEditor takes initial content once; treating it as a controlled value fights ProseMirror's internal document state. -> PREVENT: Decide the data-flow contract up front: JSON in at init, onUpdate out to a debounced server action, key-by-documentId for doc switching. No `content` prop reactivity. Encode this in the editor component's API (accept initialContent + onChange, not value) so the uncontrolled pattern is structurally enforced and reviewers see the intent. | MITIGATE: Set content once from the loaded JSON at initialization. Drive persistence OUT of the editor via onUpdate -> debounced autosave (save-on-change), never by feeding state back IN. To load a different document, remount the editor with a React `key={documentId}` rather than mutating content. If a programmatic content swap is truly needed, use editor.commands.setContent explicitly, not a prop.
- (medium/medium) Toolbar / list / heading edge cases: buttons read or toggle the wrong state — active state not reflecting the current selection, heading toggle not round-tripping back to paragraph, Enter/Tab/Backspace at list boundaries breaking, or toolbar actions firing while the editor is null or read-only. Underline in particular: it ships in StarterKit in Tiptap v3, so adding @tiptap/extension-underline separately triggers a duplicate-extension warning and can desync the toggle. -> PREVENT: Keep the toolbar to ONLY the required controls (bold, italic, underline, H1/H2/H3 + paragraph, bullet, numbered) — no tables/images/colors. Gate all toolbar rendering behind the editor-ready guard, drive active state from isActive, and add a small RTL test that clicks Bold and asserts isActive('bold') flips, catching wiring regressions cheaply. | MITIGATE: Derive every button's active state from editor.isActive(...) and disable the whole toolbar when !editor or !editor.isEditable. Rely on StarterKit's default list/heading keymaps rather than hand-rolling Enter/Tab handling.
- (medium/medium) Read-only shared-document rendering regression: a viewer (share role 'viewer') is shown an editable editor, or the read-only view is built with a different code path (e.g. dangerouslySetInnerHTML from HTML) than the edit view, reintroducing an XSS surface and/or a fidelity mismatch, and allowing a viewer to make edits the server will reject confusingly. -> PREVENT: Make editable a prop of the single editor component defaulting to false, and compute it from the server-provided role passed into the page — never from client state the user can flip. Since the meaningful test targets access-control (canView/canEdit), assert there that a viewer role yields editable:false / no write, tying the frontend read-only guarantee to the tested authorization logic. | MITIGATE: Render shared/viewer docs with the SAME Tiptap component and shared extension set but editable:false and no toolbar, driven by the server-resolved effective_role. Never branch to an HTML-injection render path. The client editable flag is UX only; the real block is the server DAL (writes require 'editor'/'owner').
- (low/medium) Large-document performance degradation: a big pasted or uploaded .md/.txt produces a large ProseMirror doc; combined with autosave serializing the full JSON on every keystroke, this causes input lag, excessive server-action traffic, and possible payload-size errors. Enforce an explicit upload size cap (well under Vercel's 4.5MB body limit) with a friendly error, and document .txt/.md + the cap in the UI/README. ### security-sharing-upload
- (high/high) IDOR / access-control bypass: a Server Action or route handler reads/mutates a document without funneling through requireDocAccess, or filters foreign rows in JS after fetching instead of in the SQL WHERE, letting user A open/edit/rename user B's doc by guessing or replaying a documentId. -> PREVENT: Write the pure authorization module src/lib/access.ts (canView/canEdit/canRename(doc, sharesForDoc, userId)) FIRST, test-first with Vitest: assert owner allowed, shared-viewer read-yes/write-no, shared-editor write-yes, non-shared user denied on all. Make the DAL the only door: route/action -> service -> requireDocAccess -> repo. No repo function accepts a documentId without a userId. | MITIGATE: Route EVERY document read/write through a single server-only requireDocAccess(documentId, session, minRole) that runs one query whose WHERE always includes the verified current userId (owner_id = me OR share.shared_with_user_id = me), computes effective_role via CASE, and throws before returning/mutating. Never filter in JS after fetch.
- (medium/high) Client-supplied identity spoofing: current userId is taken from a query param, header, form field, or client component state instead of exclusively from the signed iron-session cookie, so any visitor can POST as any user and the entire access model collapses. -> PREVENT: Bake a review rule and a test: no Server Action or service function may accept userId as a parameter — it must call verifySession() internally. Add a Vitest test that a request with no session cookie is rejected 401 and that the switcher action writes the session server-side. - (medium/high) Missing server-side authz on a subset of endpoints: authorization is enforced on reads/pages but a mutation (rename, share-grant, revoke, delete, save) skips the check or uses the wrong minRole (e.g. a shared viewer can save, or a non-owner can grant/revoke shares), because Server Actions and route handlers are directly POST-able public endpoints. -> PREVENT: Enumerate the operation->minRole matrix in code as a single source of truth and TDD it: parametrized Vitest cases proving viewer rejected on save, non-owner rejected on rename/share/revoke/delete, owner allowed on all. Middleware is UX-only, never a security boundary. Return generic not-found (not 403) to avoid existence leakage.
- (medium/medium) Unsafe file upload — oversized or wrong-type file: a reviewer uploads a large file (>4.5MB Vercel infra cap) or a non-.txt/.md file (e.g. .exe, .html, a huge .docx) and gets an opaque 413/500, or the server attempts to parse arbitrary bytes, crashing the function or degrading the demo. -> PREVENT: TDD the upload validator as a pure function validateUpload({name,size,type}) -> ok | error(code,msg): assert oversized rejected, disallowed extension rejected, .txt/.md accepted. Keep parsing strictly after validation passes. Bake the size cap constant and allowlist into one shared module imported by both the handler and the UI. | MITIGATE: Route-handler upload (runtime='nodejs') validates BEFORE parsing: check declared type/extension against an allowlist ('.txt','.md') and enforce a small explicit size cap (e.g. <=1MB) with Zod; reject with a clear 4xx and a UI toast. State supported types and cap in UI + README. .docx stays flag-gated / cut-first.
- (medium/high) Stored/rendered XSS via uploaded or authored content: raw HTML from markdown passthrough (or a future HTML path) is persisted and rendered, or a shared doc is rendered with an editable/unsanitized surface, executing script in a collaborator's session — the shared-doc render is the app's XSS blast radius. -> PREVENT: Lock the persistence contract to JSON-only in the schema and DAL from day one; forbid dangerouslySetInnerHTML on doc content via review rule. Share ONE extensions array between client editor and any server parse so no mark/node is silently introduced. Add an assertion that the shared view mounts Tiptap with editable:false, and pin/verify the DOMPurify patch level in setup. | MITIGATE: Persist Tiptap/ProseMirror JSON only (jsonb), never raw HTML, and render shared/read-only docs via Tiptap with editable:false — preserves formatting losslessly and removes the stored-HTML XSS path. If any HTML path is unavoidable (docx/markdown-raw), sanitize server-side with a patched isomorphic-dompurify (>=3.19; verify resolved dompurify >=3.3.2 via npm ls + npm audit) on the Node runtime before generateJSON.
- (medium/medium) Data leakage across My Documents vs Shared-with-me: the two lists are driven by separate flags or a client filter rather than the same server-derived source of truth, so a doc appears in the wrong bucket, a revoked/never-shared doc shows in someone's Shared list, or a list query omits the userId filter and returns foreign titles/metadata. -> PREVENT: Implement listMyDocuments(userId) and listSharedWithMe(userId) as the only list entry points, each with userId in the WHERE. - (medium/high) Session/secret misconfiguration on deploy: SESSION_PASSWORD unset in Vercel crashes iron-session at runtime, or cookie flags are wrong (secure:true on localhost breaks local run; missing HttpOnly makes the session readable to JS), or DATABASE_URL uses the non-pooled/no-sslmode host — producing runtime 500s or a weakened session on the live URL reviewers test. -> PREVENT: Write a config module that validates required env vars with Zod at import time (fail fast, clear message) and unit-test it: missing SESSION_PASSWORD throws, prod sets secure:true, dev sets secure:false.
